# 招标文件解析 — Agent 分析提示词（由 WorkBuddy 智能体逐步执行）

本文件供 WorkBuddy 智能体（skill 的属主）在「思考」步骤中遵循。脚本 `parse_toc.py` 只负责
`convert`（docx→Markdown）与 `build`（组装 JSON），中间的抽取 / 解析 / 规划 / 修订全部由 Agent 完成，
并把结果写成下列 Markdown 文件：

| 阶段 | 步骤 | 产出文件 | 依据 |
|------|------|----------|------|
| **S1 解析招标文件** | F1 | `tender-extraction.md`  | 读 `tender-full.md` |
| | F2 | `tender-index-tight.md` | 读 `tender-full.md` |
| | F3 | `tender-scoring.md`     | 读 `tender-full.md` |
| **S2 解析出响应文件** | R1 | `tender-response-docs.md`（骨架：`# 响应文件` + scope） | 读 F1 + 封装/分册要求 |
| **S3 规划各响应文件目录** | R2 | `tender-response-docs.md`（补全每个响应文件的 `## 目录`/`## 来源标注`/`## 目录说明`） | 读 F1/F2/F3 + R1 骨架 |

> `tender-response-docs.md` 在 S2 先写骨架、在 S3 就地补全，是**唯一**的目录交付中间物。
> 全部输出严禁使用 ``` 代码块包裹；目录用「无编号、真实缩进」的 Markdown 无序列表表达。

三条主路径：
- **完整分析（推荐）**：Agent 走完 S1（F1→F3）→ S2（R1）→ S3（R2），产出多响应文件目录树。
- **仅看文档结构**：`file` 子命令免 LLM，直接抽取招标文件自身的标题大纲。
- **兼容旧版单文档**：若只产出 `tender-plan-final.md`（单个合并响应文件），`build` 仍接受。

`build` 除 JSON 外还会渲染 **`tender-directory.html`**（自包含、人类可读交付物，含元信息/目录树/来源登记表，可直接打开或打印成 PDF）。

## 项目信息（可选，写在 tender-response-docs.md 顶部）

`tender-response-docs.md` 可先写一段 `## 项目信息`（**二级标题**，位于第一个 `# 响应文件` 之前；
解析器按顶层 `#` 切响应文件，`##` 会被安全忽略，不会误判为响应文件）：

```
## 项目信息
- 项目名称：南昌市烟草公司低代码采购项目
- 招标编号：NCYC2024002
- 招标人：江西省烟草公司南昌市公司
- 招标方式：公开招标
```

该段会被 `build` 提取为 JSON `meta` 字段，并显示在 HTML 顶部。没有也不影响主流程。

## S1 — 解析招标文件

### F1 — 抽取「结构要求 / 必须章节 / 模板」

读 `tender-full.md`，提取两类信息，直接输出 Markdown（从 `##` 开始，不要顶层大标题）：

```
## 一、投标文件结构要求
<对整体结构要求的概括性描述，1~3 段，含「封装/分册/装订」与响应文件划分方式>

**结构大纲：**
- 封面（附件1）
- 1. 谈判响应声明（格式见附件）
-   1.1 子项（如有）
- 2. ...

## 二、必须有的章节（mandatory chapters）
| 序号 | 章节名称 | 归属(bidPart) | 原文出处线索 |
|---|---|---|---|
（归属取值：qualification 资格 / commercial 商务 / technical 技术 / pricing 报价 / unknown）

## 三、招标方给出的章节示例 / 模板（templates）
| 序号 | 模板名称 | 归属(bidPart) | 对应必须章节 | 原文出处线索 |
|---|---|---|---|---|
```

规则：只抽文本中真实存在的内容，不编造；每条给原文出处线索；结构要求是整体框架，必须章节/模板是具体条目，二者区分清楚；模板明显对应某必须章节时填「对应必须章节」。

---

### F2 — 抽取「业务 / 技术要求」清单（raw，不做目录映射）

读 `tender-full.md`，提取项目背景 / 业务要求 / 技术要求等「要求性内容」，按主题分组，每条一行用 `|` 分隔：

```
| 需求（原文 verbatim 片段） | 出处（章/节/附件编号） |
```

**明确不抽**（属程序性/事务性/招标流程类，不是要求性内容）：封装递交、截止时间、废标/否决投标、
响应文件格式/装订/签章、合同签订及转让、联合体、保证金、准入办理、信誉承诺等。
若条款既含程序外壳又含实质义务（如"须提供 XX 资质证书"），只抽实质义务部分。

---

### F3 — 抽取「评分标准」清单

读 `tender-full.md`，提取评分标准 / 评审办法（评分项、分值/权重、评分要点），每条一行用 `|` 分隔：

```
| 评分项 | 分值 | 评分要点 | 出处 |
```

**只抽评分标准本身**；不抽资格门槛、废标/否决投标等初步评审条件（除非其带分值计入总分）。

## S2 — 解析出响应文件（R1）

读 `tender-extraction.md`（结构要求 + 必须章节 + 模板），**结合招标文件对「封装 / 分册 / 装订」的要求**
（通常在 F1 结构要求或「投标文件组成」章节），识别本次投标需要提交哪些**响应文件（独立的投标分册/分标）**。

常见划分模式：
- **分册制**：资格证明 / 商务部分 / 技术部分 / 报价部分（各自成册）
- **合并制**：单一「投标文件」整册（仅 1 个响应文件）
- **混合制**：技术与商务合并、报价单独密封等

为**每一个**响应文件，在 `tender-response-docs.md` 写出顶层结构（先写骨架，S3 补全目录）：

```
# 响应文件：技术部分
<scope 段落：该响应文件覆盖哪些章节主题、按什么依据划分（引用 F1 结构要求 /
必须章节 bidPart=technical / 模板归属）、与商务/报价部分的边界>

# 响应文件：商务部分
<scope 段落 …>

# 响应文件：报价部分
<scope 段落 …>
```

规则：
- 名称用招标文件原文措辞（如「技术部分」「商务标」「报价一览表册」）；无法确定时取通用名（资格/商务/技术/报价）。
- 若招标文件只要求**单一合并册**，仍写 1 个 `# 响应文件：投标文件`，scope 注明「整册合并」。
- scope 段落基于真实出处，不得编造；边界不清时注明「与 XX 部分边界待定」。
- scope 段落**直接写内容**，不要加 `scope：` 前缀（build 会忽略该前缀）。
- 此阶段**只写 `# 响应文件` 标题 + scope 段落**，目录在 S3 补全。

## S3 — 规划各响应文件目录（R2）

对 `tender-response-docs.md` 中**每个**响应文件，**就地**在其 `# 响应文件：XXX` 段内补全三段：

```
# 响应文件：技术部分
<scope 段落（S2 已写）>

## 目录
- 技术方案（附件N）
  - 需求理解
  - 总体设计
- 项目实施（附件M）
  - 组织结构
  - 进度计划
- …

## 来源标注
- 技术方案（附件N） :: MAND-03, REQ-11
- 需求理解 :: REQ-11
- …

## 目录说明
- 技术方案（附件N） :: 交付形态=正文编写 | 归位理由=招标规定核心技术章节 | 理由来源=MAND-03 | 概述=阐述总体技术路线与架构
- 需求理解 :: 交付形态=正文编写 | 归位理由=覆盖业务需求理解 | 理由来源=REQ-11 | 概述=对招标需求的理解与响应
- …
```

### 目录规划逻辑（对**每个**响应文件应用）

1. **以该响应文件 scope 为边界**：只在本响应文件覆盖的主题内规划，不越界到其它响应文件（已在 S2 划好边界）。
2. **骨架来源**：以 F1「结构大纲」为主线，用「必须章节（同 bidPart）」与「模板（同 bidPart）」去重、对齐顺序、补全缺失章节。
3. **层级规则**：每个有独立附件号/表号的条目（「XX 配置表（附件N）」「XX 偏离表（附件M）」）彼此平级，
   必须同一缩进层级，**严禁**互相嵌套；只有大纲本身已展开的子章节才向右缩进。
4. **无编号真实缩进**：用 Markdown 无序列表的**真实缩进嵌套**表达层级（每级 2 空格），**不要任何编号**
   （禁止 第一章/第X节/1./1.1/(1)/6. 这类前缀），只保留 `-`。可保留「附件X/表X」等标注。
5. **基于 F2/F3 查漏补缺**（覆盖而非独占）：
   - F2 需求：只要目录已有某章节 scope 能覆盖即满足，不为每条需求单开章；横切需求在相关章节分别体现；
     仅当多条需求共指明确实质主题且目录缺失时才补专属章节（挂父章节下作 L2/L3）。
   - F3 评分：评分维度都要有对应章节；评分要点提示的子内容要确保被覆盖。
6. **排除程序性条款**：封装/递交/截止时间/废标/格式/签章/合同/联合体/保证金等不进目录。
7. **顺序优化（修订③逻辑）**：先铺垫与被依赖内容（需求分析/调研/目标），再核心内容（方案/设计/实施），
   最后收尾（测试/交付/运维/保障）；同主体连续排布；不新增章节、不改名、不加编号、不跨父章节移动。
8. 只补缺、不瞎加；只做「补」与「升级/改名」，不删、不改名、不重排已有合理章节。
9. **跨目录去重互查**：同一实质内容（如"授权委托书"与资格审查子项"法定代表人授权委托书及身份证"）只保留一个目录节点，避免重复；若分属不同响应文件必须同时出现，在各自 scope 注明边界。
10. **缩进容错**：目录树每级缩进保持一致即可（推荐 2 空格；解析按相对层级，不依赖缩进宽度）。

### 来源标注格式（`## 来源标注`，全部节点）

```
- <目录节点标题（与目录逐字一致，含括号与附件号）> :: <来源ID>[, <来源ID>]
```

可用来源ID：
- `MAND-xx` = 招标文件规定的必须章节
- `REQ-xx` = 业务/技术要求
- `SCORE-xx` = 评分标准维度
- `TPL-xx` = 招标方给出的模板/格式

**编号规则（务必遵守）**：
- 数字部分**两位零填充**（写 `MAND-01`，不要写 `MAND-1`；脚本会把 `MAND-1` 自动补零为 `MAND-01`，但建议直接写对）。
- ID 编号由 F2/F3 清单的**行序**决定：**F2/F3 清单定稿后不要再插行/删行/换序**，否则目录里已引用的编号会整体漂移成悬空（build 会报 `dangling_ids` 提示）。

一个节点可对应多个来源ID；无对应来源的纯过渡/兜底章不写该行。

### 目录说明格式（`## 目录说明`，全部节点）

```
- <目录节点标题（逐字一致）> :: 交付形态=<枚举> | 归位理由=<一句话> | 理由来源=<来源ID,来源ID> | 概述=<1~2句话>
```

- `交付形态` 枚举：正文编写 / 模板或附件填充 / 混合 / 目录容器 / 待核验
- `归位理由` 只能基于该节点「来源标注」已有的来源ID作答
- `理由来源` 必须是该节点「来源标注」中来源ID的子集，无则留空
- `概述` 1~2 句话说明该节点大致交付什么；不得写我方材料、不得写具体写作步骤
- 无法判断交付形态用「待核验」，不得编造；无对应来源的节点可省略本行

## 兼容：旧版单文档 `tender-plan-final.md`

若 Agent 走的是旧版单响应文件流程（不写 `tender-response-docs.md`），则产出 `tender-plan-final.md`，

# 逐节写作细则（素材先行）

## 素材修订（默认模式）

1. **选块**：派发上下文（或指引行）已给可用素材块清单时**直接采用**——清单带
   每块的标题/字数/含图/区间/来源文件，够做规划，**无需再检索素材库**；清单缺失、
   指引标【缺】、或清单里块标「已失效」时，才按该节主题 search_references
   （写作素材库）自行检索记下命中的块 id；
   **认为指派给你的某一块与本节明显不符**（历史标书讲的行业/产品与本节主题无关、
   块内容与本节依据的要求对不上）时：该块**仍照常注入并改写**（跳过=丢图丢样式、
   改换其他块=产物路径分叉），同时用 `docx_comment_add` 留一条以「素材异议」
   开头的批注，写清块 id、不符点、本节如何处理；摘要里单列本条——指引的素材列
   归用户拍板，你只负责把问题带回去；
2. **列使用计划**：动笔前列「本节用哪几块素材、各用在哪个部分、用整块还是只用
   块内哪些行号区间」——把选块从「看过」变成「承诺」；计划里的块 id 即
   validate_body 的 block_ids（只注入了块内区间的写 blk_…:L起-L止）；
3. **贴底稿（元素级保真）**：`docx_section_create` 建节 → `docx_material_inject`
   按块 id 注入（段落/表格连合并单元格/图片零转写，格式与样式随迁；块是
   拷贝授权范围、不是注入原子——本节只需要块内某些章节时传 lines 行号区间
   只注入相关部分，整块适用则不传；同一内容区间不得进两节；仅 docx 原件可
   注入，非 docx 原件按文本参考自行撰写）——**docx 原件块禁止跳过注入直接自写**：
   图片与原样式只有注入能进正文，写作工具没有放图通道（2026-09-08 实测：
   整本自写=0 图）；
4. **改写适配**：`docx_section_read` 读视图拿段落序号 → `docx_section_revise`
   定向修订（旧项目名/公司名/参数按本次承诺清单改，围绕本项目要求调整结构）；
   保住素材的结构与事实，替换项目相关信息——全部落成 Word 修订标记；
   读视图里标〔图×N〕的段是图片段，只改其前后文字，不对图片段本身做 delete；
5. **自查**：validate_body 查素材使用率（重叠率过低=未实质使用）与疑似残留
   （素材文件名来源的旧名提示：旧项目用语替换，通用产品术语在汇报说明一句；
   元数据级旧名经 check_name_residue 扫，必须清零）。

教训（2026-09-06 实测）：不按此流程、凭自身知识自由发挥时，检索到的素材不会被
使用——质量显著下降；强制「以素材为底稿改写」后显著提升。**素材在场 ≠ 素材被用。**

## 格式跟随

按招标文件规定的格式/表格逐项响应：依据节点来源 ID → work/analysis 对应表行 →
出处列 → 按行号读 work/parse 原文取格式要求；不自由发挥结构。编号在这条链里
只是查表键（就地写时主代理自己走链；编号不进正文，见通用纪律）。

- **出处原件是 docx → 拷原件优先**：`docx_section_create` 建节 →
  `docx_source_inject`（source=来源文件名，lines=出处行号区间；独立格式附件
  留空 lines 整文件拷）把招标格式原样拷进节文件——格式逐字节保真，表格/函件
  不会重排走样；→ `docx_section_read` 拿段落序号与表格格坐标 →
  `docx_section_revise` 填空适配（表格空格子 fill、旧值 replace；招标方信息
  保留、我方信息按承诺清单填，未定值用 `docx_comment_add` 加批注记待办）；
- pdf 原件无可拷元素 → 内容一次成形于 `docx_section_create` 的 paragraphs
  （换行分段），微调走 docx_section_revise；
- **公司事实填空优先级**（资质证书/注册信息/体系认证/注册资本/员工数等
  「我们是谁、有什么」的格子）：① 派发上下文「公司材料与缺口」段的
  【知识库】命中事实——证书数字（注册号/有效期/覆盖范围）**照抄原文不改写**；
  ② 段里没有的现查 `search_company_assets`（doc_type 可过滤资质证书等类目）；
  ③ 查不到才 `docx_comment_add` 批注待办——**禁止凭印象编**（2026-09-10 接线：
  此前格式件空格只认承诺清单，公司资质类格子三不管，实测全空）。

## 临时参考件（sources/ 的类似案例）

用户上传到 sources/、明说「参考/照着写」的非招标文件（类似案例、历史标书范文）。
定位 = 写法参考；写作依据仍然是节点出处（MAND/REQ/SCORE），承诺数字仍只出自
承诺清单——案例两者都不是。

- **读法**：`parse_document` 解析（同名幂等）→ 先读 outline.json 按行号取相关
  区段，禁止整读全文（案例动辄几十页，整读烧 token 也读不细）；
- **只借写法不抄事实**：章节组织、论证顺序、表格设计、语言风格可借鉴；案例里的
  项目名/客户名/公司信息/数字/日期一律不进正文——残留扫描对这类文件**没有防线**
  （文件名不在素材库元数据里），纪律是唯一防线；
- 与招标要求冲突时以招标文件为准（案例不是依据）；
- 案例叙述性内容进正文的唯一形态是**改写**，不整段拷贝（`docx_source_inject`
  是给招标格式件的窄口径工具）；确有值得原样搬的表格样式/版式结构时，先在
  摘要里带回说明再动；
- 案例不进 block_ids（不是素材块，使用率校验不管它）——用了案例哪些写法在
  完成摘要里说明，否则主线程查不出「读了没用」。

## 物理附件（复印件类）

资质证书复印件、营业执照副本、票据凭证、信用查询截屏等物理附件位（目录形态
=模板或附件填充）——**每个附件位在整本里都必须有落点**（2026-09-14 拍板）：

- **指引缺口列有【知识库】命中（含图）→ 贴图产出节文件**：`docx_section_create`
  建节 → `docx_image_insert` 逐张贴证书图（图源路径按命中注明的
  knowledge/parse/…/images/；PDF 原件传路径+页号按页渲染）——贴图写法与
  推理撰写节的证书图片指令相同；库里没有的证书不硬凑，`docx_comment_add`
  批注点名待线下补；
- **全无命中 → 建壳节**：`docx_section_create` 建节——标题 + 一行贴入位
  「（此处贴入：XXX 复印件，加盖公章）」（与招标件自印「在此粘贴身份证
  复印件」同一惯例：材料贴上去即覆盖，不存在忘删占位文字的问题），再
  `docx_comment_add` 批注点名缺什么材料、需要谁提供；收尾汇报仍逐条点名。
  废标级资格件（营业执照这类缺了直接否决的）绝不许只登记不建节。

## 封面

树首「封面」节点的成形（合册时它是整本第一页、独占一页、不带页眉页脚，册名
大标题也不另发——封面自带）：

- **招标有封面格式样例且原件 docx** → 走上面格式跟随的拷原件路径：拷样例 →
  revise 填投标人名称/日期等空位（日期用任务描述给的「今天日期」）；
- **无样例或样例是 pdf** → 排版成形：`docx_section_create(title="封面")`
  建节（标题段合册时自动剥掉，不用管）→ `docx_section_revise` 逐行
  insert_after 插封面行，**每行带 `"style"` 字段指定版式**：大字行（项目名/
  「<册名>」）用 `"Tender Cover"`，落款行（投标人：xxx / 日期：xxxx 年 x 月）
  用 `"Tender Cover Sub"`；下沉定位插全角空格行（text 用「　」——空字符串
  会被工具拒、全角空格行合法），标题块前 3~4 行、落款块前 4~6 行；
- 字段值纪律：项目名/册名从目录与任务描述取；投标人名称等只从承诺清单取
  （缺→加批注待办，不编造）；日期只写任务描述给的「今天日期」（天级精度），
  **禁止自编日期**；版式库里没有这两个样式名时工具会回落正文样式并在返回里
  注记——照常交付，向主代理带回一句即可。

## 推理撰写

针对本项目写方案（技术路线、实施步骤、保障措施）：

- 全文一次成形于 `docx_section_create` 的 **body 块序列**（段落+表格混排，
  2026-09-14 起）——不逐段 insert_after 拼长文（多次小编辑既慢又易错位），
  局部补充才用 revise；纯文字节仍可用 paragraphs（换行分段）；
- **表格类内容（人员配置/里程碑/进度计划/对比清单）用 table 块，不用流水句铺**
  ——评委按表找要点比按段落找快，流水句里的「（一）项目经理，1 名，签订在
  合同中。职责是…」就是该成表没成表的形态。写法示例：

  ```json
  [
    {"type": "p", "text": "我方组建专职实施团队，按招标文件第五章岗位口径配置，如下表："},
    {"type": "table", "caption": "项目团队岗位配置",
     "header": ["岗位", "人数", "职责", "是否签入合同"],
     "rows": [["项目经理", "1", "对本项目交付负总责，全程现场参与并主导实施", "是"],
              ["架构师", "1", "主持总体技术架构与集成方案设计", "是"]]},
    {"type": "p", "text": "同一成员可按招标口径兼任多个角色，兼任不降低履行质量。"}
  ]
  ```

  （建节时作 body 参数传入；表题自动落表格上方居中，表头自动加粗浅灰，落格
  文字可编辑、validate_body 可读回做承诺对账——工期/人数等承诺值落表格格，
  不落图片。）
- **图示按指引图示列的计划产出**（计划先行，收尾对账）：分层架构/组织架构
  =`docx_diagram_insert(kind="layered")`、实施进度计划=`kind="gantt"`
  （任务+周次，start/end 为周号；里程碑单列 ◆ 行）、以某物为中心的关系
  =`kind="radial"`——模型只给语义拓扑（层/任务/中心与两翼），灰阶版式程序
  机械生成；**带分支回环的流程图**（故障处置/审批流转）=`kind="flow"`——给
  节点+连线的 JSON 拓扑（判断节点 shape="diamond"、起止 shape="round"、边
  第三元素写「重大/一般/是/否」标签），程序转 mermaid 渲染成图，模型不写
  mermaid 文本；纯叙述内容不配图（加图不加分），承诺函/函件类格式节禁配；
  flow 用法示例：
  `{"nodes":[{"id":"a","label":"提交故障"},{"id":"b","label":"判定级别","shape":"diamond"},
  {"id":"c","label":"应急处置"}],"edges":[["a","b"],["b","c","重大"]]}`；
- 承诺类数字（工期/人员/服务/报价口径）只引「关键事实与承诺」清单值；
- 企业事实优先用派发上下文「公司材料与缺口」段的【知识库】命中事实（数字
  照抄）；段里没有的现查 search_company_assets 并可溯；拟投入承诺不是现状
  事实，数字一律重核；
- 证书复印件/奖牌/系统截图等图片用 `docx_image_insert` 插入（图源路径出自
  检索命中行的「含图 N 张」提示；原件是 PDF 时传路径+页号按页渲染）——文字
  陈述证书、图片贴在陈述段之后，每张一次调用。

## 界面原型（docx_html_figure）

方案节要展示「系统长什么样」时（指引图示列计划了「原型:…」），用原型图代替
大段文字描述界面。模型只写 HTML，渲染由应用前端完成（离线、自动带角标）：

- **全部样式内联**（`<style>` 或 style 属性）——外链 CSS/字体/图片会被内容安全
  策略拦掉，页面缺件；图片确需示意可用 data: URI；
- **禁脚本、禁外链**（会被剥除/拦掉）；≤150 行、≤100KB；
- 画桌面端界面（视口约 1200px）：顶栏/侧栏/内容区用 flex 布局，按钮、表格、
  标签页等控件用简单样式表达，灰阶为主不过度配色——这是示意不是视觉稿；
- 位置：先一段文字铺垫（该界面的用途与关键能力），原型图紧随其后，再一段
  要点对照（图中区块对应的能力说明写进文字段）；
- 渲染失败（应用不在前台等）时**改用文字描述界面 + docx_comment_add 批注记
  「界面原型待补」**，勿原地重试。

## 通用纪律

- 缺料不阻塞：`docx_comment_add` 加批注（锚定相关段落）继续写；待澄清/待核验
  同样落批注；**正文禁止【待补】【待澄清】占位文字**（会随交付稿打印出去）；
  批注收尾必须逐条点名；
- **标题不带数字编号**：建节 title 用目录里的原文名（合册剥节文件自带标题
  按裸名对账，带编号会剥不掉、双标题）；节内小标题同样不写「一、」「1.1」式
  编号——章节编号由合册按目录树序自动加，模型自编编号必错（不知道树位置），
  层级用 Heading 2/3 样式表达；素材拷入的标题段若自带 Word 自动编号，
  注入与合册会程序剥除（正文列表编号保留），看到带号标题不必重建段落；
- **节内小标题逐级递进**：从二级（Heading 2）起、不跳级不倒挂（二级下面才能
  出三级），层级跳来跳去会让 Word 导航窗格和自动目录结构混乱——合册会把节内
  小标题摘出整本大纲（导航只显示章节骨架），**并按树深度自动降一级、程序接续
  节号**（深度 2 节下 H2→H3 并编号 5.1.1 式——编号归合册程序，写手一个号都
  不写；节文件内的层级仍按本纪律写对）；
- 正文不带模型写的头部/元信息（干净文本，评委要看的是干净文本）；
- REQ/MAND/SCORE/TPL-xx 是内部对账编号，一个都不写进正文（无论从指引、目录
  还是任务描述里看到）；呼应招标要求用要求内容本身或招标文件真实印着的章节/
  条款号（如「按第三章 2.3 条」——评标人能对照原文，内部编号他们对不上）；
- 写节前浏览同层已写节的开头段（主线程就地写时），或对照任务描述里的兄弟节
  开头摘要（子代理派发时）——避免跨节重复表达；
- 一节写完即 validate_body 自查，不留到最后；
- 重写已存在的节：建节传 replace=true（旧版自动入恢复点栈），不要试图直接
  覆盖写。

## 语言纪律（生成文字去 AI 腔）

裁剪自 `skills/humanizer-zh/SKILL.md`（通用润色技能）按标书场景适配；完整规则
与评分表见原技能，正文写作只守本节。

**作用域**：只管模型自己生成的文字——推理撰写的全文、素材修订里新增/改写的
段落、格式跟随里自写的说明文字。注入的素材底稿与拷贝的招标格式件**原样保留
一个字不润**：为去腔重写素材会掉素材使用率重叠率（被判「未实质使用」）、破坏
保真语义；动招标方的格式件是事故。

七条规则（改写前 → 改写后）：

1. **删填充语**：「为了实现这一目标，我们将…」→「我们将…」；
   「值得注意的是，系统支持…」→「系统支持…」；
2. **删夸大修辞**：「标志着」「至关重要」「彰显了」「奠定坚实基础」「保驾护航」
   ——评审看的是逐条响应了什么要求，不看抒情；「为后续运维奠定坚实基础」→
   删掉，写实际措施；
3. **禁模糊归因**：「行业专家认为」「大量实践证明」「业界普遍认同」→ 引具体
   事实（同证据纪律）或整句删——给不出出处的归因不写；
4. **拆强行三段式**：凑三点、凑对仗排比改为按实际内容组织，有几条写几条
   （「高效、可靠、安全」三连多半是凑的）；
5. **删句尾肤浅分析**：「……，确保了项目顺利开展」「……，为后续工作提供了
   有力支撑」——尾缀删掉，句子到事实为止；
6. **删空洞承诺结尾**：「我们有信心、有能力、有决心圆满完成…」→ 删，用具体
   措施与承诺清单值收尾；
7. **少用否定式排比**：「这不仅是一次系统部署，更是管理理念的升级」→ 直接写
   部署了什么、解决了什么。

标书允许规整句式（评审按点扫描，结构清晰是优点）——要避免的是每段同长同构
叠加空洞修辞，不是句式本身。

## 子代理执行（并发派发）

并发派发的子代理（tender-body-writer）额外遵守：

- 任务描述=首行节名清单（一节或多节，2026-09-15 起任务可捆多节）与意图＋系统
  自动附上的派发上下文（各节路径/模式/要求清单/素材块/公司材料与缺口/承诺清单
  全部值/兄弟节摘要）——已含全部共享信息，**禁止再读 `work/body/写作指引.md` 与

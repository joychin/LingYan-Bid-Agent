# 节：商务技术要求（requirements-business）

只抽取投标人必须响应的**商务、技术、服务、交付实质要求**。输出
`out/analysis/requirements-business.md`。

## 提取范围

项目背景中对我方的实质性期望、商务要求、技术要求、服务要求、交付与验收要求等
「要求性内容」。

## 明确不抽（程序性/事务性/招标流程类，不是要求性内容）

封装递交、截止时间、废标/否决条款、响应文件格式/装订/签章、合同签订及转让、联合体、
保证金、准入办理、信誉承诺——这些属于其他节的职责。
条款既含程序外壳又含实质义务（如「须提供 XX 资质证书」）时，只抽实质义务部分。

## 判定边界

- 每条是可独立核查的要求；不编造企业能力、产品参数、案例、人员或承诺。
- 条款体来源（一行一条的规格/要求）：需求原文保持 verbatim 片段（截取关键句即可，
  不整段粘贴，不转写语义）。叙述型来源按下节纪律拆条。

## 叙述型来源的拆条纪律（需求说明书/业务场景白皮书类补充文件）

叙述体没有现成的「需求句」，需先解读出功能点再登记。REQ 表是偏离表逐条响应的
机器输入，粒度必须与条款体来源对齐：

- **拆条粒度**：按 outline 小节或功能点拆条，一条 = 一个可独立响应的功能要求；
  **禁止把整个模块/章节压成一条**——多功能点串成 mega 行会让下游偏离表无法逐条
  响应、评分覆盖度统计失真，且后续细化会引发编号整体重排。
- **verbatim 变通**：关键短语照抄 + 行段出处；可删主语、场景铺垫（无损删节）；
  **不得改写语义，不得丢弃原文的模糊表述**——「按照某种机制分配」这类原文未
  定义处，照抄进条目并登记待澄清（模糊本身就是需要用户裁决的信号，转写会把它
  洗掉）。
- **背景不进表**：纯场景背景、行业铺垫不写入 REQ 表（在 coverage 声明中说明即可），
  可独立核查的功能点才登记。
- **与主文件重叠**：补充文件叙述与主文件已登记条款实质重叠时**不重复登记**——
  在对应主文件条目的出处追加补充行段（如「…L322；需求说明书.pdf L16-L28
  （场景补充）」）；仅当补充文件含**新功能点**时才立新条目。

## 输出格式（REQ 登记表机器输入，行序=编号，定稿后不插行/删行/换序）

```
（第一行头部元信息注释）
## 商务技术要求清单
| 需求（原文 verbatim 片段） | 出处（章/节/附件编号） |
|---|---|
| 系统须支持 500 并发用户 | 招标文件.docx 第三章 技术要求 2.1（L208） |
| 提供三年免费运维服务 | 同文件 第五章 服务要求（L342） |
| 约访结果按「待跟进/拒绝拜访/已跟进/已签约」填写 | 需求说明书.pdf 线索跟踪（L16-L28，第1页） |

## 待澄清登记
-（有则列，无则省略）

## coverage 声明
已检查：…；未检查：…
```

## 禁止

不抽资格准入、递交程序、废标后果、格式装订、签章、保证金、评分规则。

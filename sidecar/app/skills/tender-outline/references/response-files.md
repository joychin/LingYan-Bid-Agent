# R1：响应文件分解

识别本次投标需要提交哪些**响应文件**（独立的投标分册/分标/单独递交的逻辑文件实体），
写出 `work/outline/tender-response-docs.md` 骨架。

## 输入

- `work/analysis/requirements-format.md` 的「一、投标文件结构要求」（封装/分册/装订要求、
  结构大纲）——划分的主要依据；
- `work/analysis/structure.md`（标段划分：分标段投标时通常每标段一套响应文件）。

## 常见划分模式

- **分册制**：资格证明 / 商务部分 / 技术部分 / 报价部分各自成册（每册一个响应文件）；
- **合并制**：单一「投标文件」整册（仅 1 个响应文件）；
- **混合制**：技术与商务合并、报价单独密封等。

## 骨架格式

```
## 项目信息
- 项目名称：<structure.md 的项目名称>
- 招标编号：<有则写>

# 响应文件：技术部分
<scope 段落：该响应文件覆盖哪些章节主题、按什么依据划分（引用 format 节的结构要求 /
必须章节 bidPart / 模板归属）、与商务/报价部分的边界>

# 响应文件：商务部分
<scope 段落 …>
```

## 规则

- 名称用招标文件原文措辞（如「技术部分」「商务标」「报价一览表册」）；无法确定时取
  通用名（资格/商务/技术/报价）。
- 招标文件只要求**单一合并册**时，仍写 1 个 `# 响应文件：投标文件`，scope 注明「整册合并」。
- **正副本、电子版、U 盘、加密件、封套、份数是递交 metadata，不是独立响应文件**；
  只有原文明确独立处理（如「报价一览表单独密封递交」）时才拆出。
- scope 段落基于真实出处，不得编造；边界不清时注明「与 XX 部分边界待定」。
- scope 段落直接写内容，不加 `scope：` 前缀。
- 此阶段**只写标题 + scope**，目录在下一步补全。

## 确认点操作

两问测试的①不满足（方案唯一、证据充分）→ 径直继续。
存在多种合理方案或证据不明 → `ask_human`：
- question 第一行问选哪种拆分方案（含项目背景与依据），换行后一句影响说明
  （拆分决定下游目录结构与各册分工，选错会大面积重做）；
- options 用「；」分隔各方案，依据更充分的方案尾加「（推荐）」
  （如「三册分立（资格/商务/技术）（推荐）；技术商务合并+报价单独」）；
- 用户答复里的补充意见（如「报价和技术合并」）直接按用户方案执行。

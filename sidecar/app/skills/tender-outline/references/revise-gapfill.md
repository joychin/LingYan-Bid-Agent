# 清理①：查漏补缺（STEP3，原则从老流水线逐字保留）

基于 `out/analysis/requirements-business.md` 的 **REQ 需求清单**，对当前目录做查漏补缺：
检查目录是否遗漏了需求清单里明确提出的、必须响应的内容，把缺失的章节补上。

**跳过条件**：requirements-business.md 无 REQ 条目（此时向用户声明后跳过本道）。

## 判定原则（先判「是否真的缺」，再决定加在哪一级）

1. **覆盖而非独占**：逐条核对需求清单——只要目录里已有某个章节的**范围能够覆盖**该需求，
   就视为已满足，无需新增；只有当目录中**没有任何章节的 scope 能覆盖该需求**时，才补章节。
   不要为每条需求都单独开一章，多个需求被同一章节覆盖是常态。
2. **横切需求**：若某需求涉及多个技术/业务方面（如「高扩展性」同时关联 技术架构、性能设计、
   数据库设计），应在所有相关章节中分别体现，而不是只塞进一个章节、也不强迫合并成一个新章。
3. **实质主题成章**：若需求清单里**多条**需求共同指向同一个明确的实质主题，且目录里
   **没有对应该主题的章节**，才为该主题补一个专属章节：属于技术方案/业务核心内容的，
   挂在其所属父章节（如技术方案）下作 L2，并可拆 L3；仅当该主题实质上是整个项目的
   主要交付内容时，才考虑独立 L1。不要因为一两条小需求就强行升 L2/L1。

## 禁止与边界

4. **排除程序性条款**：封装、递交、截止时间、废标项、响应文件格式/装订/签章、合同签订
   及转让、联合体、保证金、准入办理等属招标流程/程序性条款，不进目录、也不进「其他」。
5. **只补缺、不瞎加**：不新增招标文件/需求清单里没有依据的内容；只补「需求清单明确有、
   但目录缺失」的部分。
6. 本道只做「补」，**不删、不改名、不重排**已有的合理章节。
7. **保持格式**：每行以 `- ` 开头 + 无编号 + 真实缩进；同一层级条目保持并列，
   不要因原文两条相邻就强行套成父子。

## 操作方式

读当前 `## 目录`（A）与 REQ 清单（B）→ 逐条核对 → 新增节点挂 `来源标注 :: REQ-xx`
与 `## 目录说明` 行 → 保持其余内容原样。
